# 17. Redis 分布式缓存

> 本教程基于 **Spring Cache + Spring Data Redis + Redisson**
> Spring Boot 4.0.6 + Spring Cloud Alibaba 2025.1.0.0
> 难度：⭐⭐ | 预计时间：45 分钟

## 一、为什么需要缓存？

每次请求都直查 MySQL 的问题：

- **响应慢**：单次 SQL 至少 5-20ms
- **数据库压力大**：高并发下连接池耗尽
- **难以应对突发流量**：618、双11 等场景

**Redis 作为缓存层的优势**：
- 内存存储，读写速度 10w+ QPS
- 支持丰富的数据结构（String/Hash/List/Set/ZSet）
- 支持持久化、主从、集群
- Spring Cache 抽象让缓存接入零侵入

## 二、缓存三大问题

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 查询不存在的数据，每次都穿透到 DB | 布隆过滤器 / 缓存空值 |
| **缓存击穿** | 热点 key 过期瞬间大量请求打到 DB | 互斥锁 / 逻辑过期 |
| **缓存雪崩** | 大量 key 同时过期 / Redis 宕机 | 随机过期时间 / 多级缓存 / 熔断降级 |

本项目通过 **Spring Cache + Redisson 分布式锁** 综合解决。

## 六、缓存配置类

```java
@Configuration
@EnableCaching
public class CacheConfig {
    
    @Bean
    public RedisCacheConfiguration redisCacheConfiguration() {
        return RedisCacheConfiguration.defaultCacheConfig()
                .serializeValuesWith(RedisSerializationContext.SerializationPair.fromSerializer(
                        new GenericJackson2JsonRedisSerializer()))  // JSON 序列化
                .entryTtl(Duration.ofMinutes(10));
    }
}
```

**关键点**：
- `GenericJackson2JsonRedisSerializer` 会带类型信息，反序列化无需 `@Class`
- 不要用默认的 `JdkSerializationRedisSerializer`（Java 二进制格式不可读）

## 七、注解式缓存（核心）

### 7.1 @Cacheable - 查询走缓存

```java
@Override
@Cacheable(value = "user", key = "'user:id:'+#id")
public UserDomain findById(Integer id) {
    return userDao.findById(id);
}
```

**SpEL 表达式说明**：
- `#id`：方法参数
- `#result`：返回值（用于 @CachePut）
- `#root.methodName`：方法名
- 字符串必须加单引号：`'user:id:'`

**执行流程**：
1. 查 Redis 是否有 `sca:user::user:id:1`
2. 有 → 直接返回（不执行方法体）
3. 无 → 执行方法体，将结果写入 Redis

### 7.2 @CacheEvict - 修改/删除失效缓存

```java
@Override
@CacheEvict(value = "user", allEntries = true)  // 清空整个 user 命名空间
public int insert(UserDomain record) {
    return userDao.insert(record);
}

@Override
@CacheEvict(value = "user", key = "'user:id:'+#userId")
public void deleteUserById(Integer userId) {
    userDao.deleteUserById(userId);
}
```

**`allEntries = true` vs 指定 key**：
- `allEntries = true`：清空该命名空间下所有 key（适合批量更新）
- 指定 `key`：只清空单个 key（精细控制）

### 7.3 @CachePut - 更新缓存

```java
@Override
@CachePut(value = "user", key = "'user:id:'+#user.id")
public UserDomain updateUser(UserDomain user) {
    userDao.updateUser(user);
    return user;  // 返回值会写入缓存
}
```

**与 @CacheEvict 的区别**：
- `@CachePut` 先执行方法体，再把返回值写入缓存
- `@CacheEvict` 直接清空缓存

## 八、缓存策略

### 8.1 Cache Aside Pattern（最常用）

```
读流程：
  1. 读 Redis
  2. 命中 → 返回
  3. 未命中 → 读 DB → 写 Redis → 返回

写流程：
  1. 写 DB
  2. 失效 Redis（@CacheEvict）
  3. 下次读时重新加载
```

**为什么是"失效"而不是"更新"？**
- 并发更新可能产生脏数据
- 懒加载思想：避免无效写入

### 8.2 防缓存击穿：Redisson 分布式锁

```java
public UserDomain findByIdWithLock(Integer id) {
    String key = "user:id:" + id;
    // 1. 先查缓存
    UserDomain cached = (UserDomain) redisTemplate.opsForValue().get(key);
    if (cached != null) return cached;
    
    // 2. 缓存未命中，加锁查 DB
    RLock lock = redissonClient.getLock("lock:" + key);
    try {
        lock.tryLock(3, 10, TimeUnit.SECONDS);  // 等待 3s，锁 10s 自动释放
        // 双重检查：可能其他线程已加载
        cached = (UserDomain) redisTemplate.opsForValue().get(key);
        if (cached != null) return cached;
        
        // 3. 查 DB 并写入缓存
        UserDomain user = userDao.findById(id);
        if (user != null) {
            redisTemplate.opsForValue().set(key, user, 10, TimeUnit.MINUTES);
        }
        return user;
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new RuntimeException("获取分布式锁失败", e);
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

**Redisson 看门狗机制**：
- `lock.lock()` 默认启动看门狗，每 10s 自动续期（leaseTime/3）
- 避免业务执行时间超过锁超时时间导致锁失效
- 显式指定 `leaseTime` 会关闭看门狗

## 十、性能对比

| 场景 | 无缓存 | 有缓存（命中） | 提升 |
|------|--------|---------------|------|
| 单次查询 | 15ms | 0.5ms | **30x** |
| 1000 并发 | DB 压力大，可能超时 | Redis 轻松应对 | **100x+** |
| 突发流量 | DB 雪崩 | 缓存吸收 | **抗住流量** |

## 十一、常见问题

**Q1：缓存与 DB 数据不一致？**
- 采用 Cache Aside + 短 TTL（10 分钟）方案
- 强一致场景：读 DB 后写缓存时加分布式锁
- 最终一致：容忍短时间不一致

**Q2：@Cacheable 的 key 不生效？**
- 确认 SpEL 表达式正确
- 字符串必须加单引号
- 复杂对象用 `keyGenerator` 而非 `key`

**Q3：Redis 连接池耗尽？**
- `max-active` 调大（生产建议 50+）
- 检查是否有连接泄漏（未关闭 RedisTemplate）
- 使用 Lettuce 而非 Jedis（线程安全，可复用连接）

**Q4：Redisson 锁死锁？**
- 不要在 finally 外面 unlock
- 启用看门狗自动续期
- 监控 Redis 中残留的 key：`KEYS lock:*`

## 十二、小结

| 注解 | 作用 | 典型场景 |
|------|------|---------|
| `@Cacheable` | 查询走缓存 | 详情页、配置项 |
| `@CacheEvict` | 失效缓存 | 新增/更新/删除 |
| `@CachePut` | 更新缓存 | 需要返回最新值 |

**生产最佳实践**：
1. **缓存粒度**：按业务主键，不要缓存大对象
2. **TTL 设置**：根据数据更新频率，宁短勿长
3. **监控**：Redis 内存使用率、命中率（`info stats`）
4. **降级**：Redis 不可用时直接走 DB（不要让缓存故障拖垮系统）
